# ESP32 RAM Audit — 2026-11-04

## Scope and safety constraints

This audit is based on the current `master` source snapshot and is intentionally non-invasive. It does not change inverter control, ADC/ISR ownership, Wi-Fi lifecycle policy, TLS settings, OTA download buffers, certificate verification, or firmware installation. The target ESP32 build has no configured PSRAM, so internal RAM and contiguous internal blocks are the limiting resources.

## Existing instrumentation found

- `src/main.c` already logs free 8-bit heap and largest free block at startup-supervisor stage boundaries, and logs the Bluetooth-memory-release delta.
- `src/diagnostics/stack_report.c` already reports task stack high-water marks and total unused stack. Its call in `src/app_services.c` is immediately before OTA installation, which is a useful high-pressure snapshot.
- `src/server/network_services.c` already records heap snapshots around HTTP, dashboard, JSON API, WebSocket, mDNS startup and teardown (`NS_HEAP`).
- The network-services and stack-report snapshots previously reported only general 8-bit heap. This branch adds internal 8-bit free heap and largest internal block to both, which is more useful for allocations that must reside in internal RAM (including TLS).

## High-cost allocations to measure before changing

| Area | Current source setting | Why it matters | Action |
|---|---:|---|---|
| Main task | 8192-byte configured stack | Long startup orchestration and initialization call depth | Keep until stack report includes a worst-case startup sample |
| LCD task | 6144 bytes | Rendering/menu call depth; source comment records 3828 bytes minimum-ever free from an earlier 8192-byte stack | Do not reduce based only on this historical sample |
| Event tasks | 2048–4096 bytes | Fault/event call paths differ by task | Measure each task during fault/event bursts |
| HTTP server | 8192-byte task stack; 6 open sockets | Persistent WebSocket plus REST clients; stack and sockets both consume resources | Keep behavior; measure live heap and high-water under concurrent dashboard use |
| HTTPS server | 10240-byte task stack; 3 open sockets | TLS server has larger call depth and per-connection allocations | Do not reduce without TLS server stress measurements |
| Network sync task | 8192-byte stack | NTP/MQTT/network lifecycle work | Measure on-device |
| mDNS | 4096-byte stack, internal allocation enabled | Additional internal-RAM consumer | Avoid disabling unless feature requirements change |
| Wi-Fi | 8 static RX buffers, 16 dynamic RX buffers, 16 dynamic TX buffers in the checked sdkconfig template | Driver throughput/latency trade-off and internal memory use | Tune only with packet-load and reconnect regression tests |

## Findings

1. The project already contains substantial heap and stack instrumentation. The immediate gap was that network lifecycle and stack reports did not distinguish general 8-bit heap from internal 8-bit heap.
2. The OTA path explicitly checks the largest internal block and suspends local HTTP/WebSocket/mDNS/NTP/MQTT services before TLS download. Preserve this behavior and the working TLS/download buffers.
3. The HTTP server is configured for six open sockets. This is a deliberate concurrency setting for dashboard WebSocket plus REST polling, not an obvious memory leak. Reducing it may reintroduce WebSocket eviction; increasing it may increase socket and lwIP memory use.
4. The stack report enumerates application and system tasks by task name, but only tasks that exist at the instant of the report are included. On-demand tasks (scan, OTA checks, Wi-Fi toggles) must be sampled while active to understand their peak stack usage.
5. No safe task-stack reduction can be justified from source inspection alone. A high-water value is valid only after the relevant task has experienced its deepest realistic call path; a percentage reduction without that measurement risks stack overflow.
6. No blanket reduction of Wi-Fi buffers, TCP windows, TLS content lengths, or OTA HTTP buffers is recommended. These can affect reliability and OTA, and the repository has previously experienced TLS contiguous-allocation failures.

## On-device measurement procedure

1. Build and flash this branch, then capture the boot log from reset.
2. Exercise normal inverter operation, LCD menus, Wi-Fi AP/STA, concurrent dashboard polling and WebSocket, MQTT/NTP where enabled, Wi-Fi reconnects, and a failed/cancelled OTA check.
3. Capture the `STACK_REPORT` immediately before OTA and the `NSHEAP` start/stop lifecycle sequence. Compare `heap8`, `largest8`, `internal`, and `largest_internal`.
4. Repeat after a full Wi-Fi/service stop and restart. A persistent reduction after restart indicates a lifecycle leak or retained allocation; a transient drop while services are active is expected.
5. For stack tuning, record each task's stack allocation and minimum-ever-free value after its worst-case activity. Calculate observed peak use as allocation minus minimum-ever-free, then retain a conservative margin (at least 25%, and more for ISR-adjacent or protection-critical paths). Confirm the units used by this ESP-IDF build before interpreting high-water values.
6. Do not run a firmware update while testing experimental stack or buffer reductions. First validate the existing known-good OTA path unchanged.

## Next optimization candidates (pending measurements)

- Consider stack reductions only for tasks whose measured worst-case high-water marks show large, repeatable unused margins.
- If service restart snapshots show unrecovered internal heap, trace the exact start/stop owner and allocation before changing lifecycle code.
- If JSON/API traffic causes fragmentation, profile allocation sizes and concurrency before introducing shared static buffers; shared buffers require explicit serialization and must not be used from ISR contexts.
- Consider reducing Wi-Fi buffer counts only after throughput, reconnect, AP provisioning, and dashboard stress tests demonstrate excess headroom.

## Validation status

Source-level audit and diagnostic expansion only. No PlatformIO build or physical-device test was available during this pass. No claim of RAM savings or runtime stability is made until device logs are collected.
